# Implementation Plan

This plan intentionally stops before runtime implementation. Each milestone has a reviewable outcome and a validation boundary.

`src/` will initially use portable POSIX shell plus small utilities already common on embedded Linux. A parser/schema implementation may be chosen during Milestone 1 based on image constraints; it must not turn configuration into shell-evaluated code.

## Milestones

### 0. Research and architecture baseline

**Deliverables**

- `docs/architecture.md` with source links, explicit unknowns, configuration contract, lifecycle model, and risk register.
- `docs/implementation-plan.md` with this milestone breakdown.
- `config/example.yaml` containing placeholders only.

**Exit criteria**

- No product-specific identity is present in source or example configuration.
- All claims about Windows binding that lack authoritative documentation are marked for hardware validation.

### 1. Configuration schema and validation

**Deliverables**

- Machine-readable schema for USB identity, MAC addresses, IPv4, DHCP, IPv6, gadget name, UDC selection, and optional NCM tuning.
- Parser/validator with useful field-level errors.
- Tests for valid data, malformed VID/PID, placeholder production rejection, invalid MACs, subnet/address mismatch, duplicate identities, and unsupported enum values.

**Exit criteria**

- Validation completes without touching ConfigFS.
- The same input produces the same normalized configuration.
- Secrets or raw hardware identifiers are not required in the generic format.

### 2. ConfigFS transaction engine

**Deliverables**

- Mount detection and optional ConfigFS setup.
- Kernel capability checks for `libcomposite`, `usb_f_ncm`, required files, and at least one UDC.
- Idempotent gadget creation, configuration linking, NCM function setup, and UDC binding.
- Rollback and teardown paths that remove only resources owned by this gadget.

**Exit criteria**

- Fake-ConfigFS tests cover create, repeated create, stop, repeated stop, and failure at every mutation step.
- No hard-coded UDC or resulting network-interface name is used.
- Logs identify the failed operation and cleanup result.

### 3. Device network lifecycle

**Deliverables**

- Runtime discovery of the NCM-created net device using sysfs/udev relationships.
- Device MAC application and link setup.
- Device-served DHCP profile with fixed host lease, plus static IPv4 profile.
- Explicit IPv6 disabled/link-local behavior.

**Exit criteria**

- Repeated network-device add/remove events converge to one configured interface.
- Network configuration does not change unrelated interfaces.
- CI tests use mocked netlink/sysfs state; hardware tests cover actual interface recreation.

### 4. systemd integration and recovery

**Deliverables**

- Start/stop units with ordering for local filesystems, ConfigFS, UDC availability, and networking.
- Runtime recovery for USB disconnect/reconnect, gadget recreation, and embedded reboot.
- Bounded retries with clear journal messages.

**Exit criteria**

- Boot and shutdown are deterministic on a representative systemd image.
- Recovery does not require a reboot or manual Windows adapter changes.
- Failure leaves the gadget either fully absent or fully configured.

### 5. Descriptor inspection and standards validation

**Deliverables**

- `usb-inspect` helper and captured descriptor fixtures.
- Descriptor validator for device/configuration/interface/endpoint structure, CDC class values, control/data association, functional descriptors, and speed-specific differences.
- `docs/usb-descriptors.md` explaining what is generated by the kernel versus validated by the project.

**Exit criteria**

- Captured descriptors are parseable and match the CDC-NCM contract.
- Exact kernel-dependent values are fixture-specific rather than presented as universal constants.
- Full/high/super-speed results are recorded where the UDC supports them.

### 6. Windows compatibility qualification

**Deliverables**

- `tools/windows-diagnostics.ps1` reporting enumeration, VID/PID, serial, PnP state, driver service/image, adapter state, addresses, routes, and connectivity.
- `docs/windows-compatibility.md` with tested Windows 10/11 editions/builds, driver selection, INF findings, and known limitations.
- SetupAPI and descriptor captures for every tested host build.

**Exit criteria**

- The matrix states exactly where `UsbNcm.sys` binds, where it does not, and what evidence supports each result.
- No custom driver installation is performed.
- Any INF is optional metadata/naming support only and is never used to replace the inbox driver without a documented decision.

### 7. Hardware interoperability and persistence

**Deliverables**

- Hardware test harness and repeatable test procedure.
- Tests for disconnect/reconnect, Windows reboot, embedded reboot, gadget recreation, network-interface recreation, multiple devices, and composite variants.
- Stable serial/MAC provisioning guidance.

**Exit criteria**

- No unnecessary duplicate Windows adapters are created in the supported identity scenarios.
- Device and host can exchange traffic after each recovery event.
- Throughput, latency, suspend/resume, and error behavior are recorded.

### 8. Production packaging and migration

**Deliverables**

- Install and uninstall mechanisms.
- `README.md`, Linux requirements, networking, troubleshooting, and RNDIS migration documentation.
- Placeholder `LICENSE` selected by repository owner.
- CI checks for shell syntax, schema/config tests, descriptor fixtures, and documentation links where tooling permits.

**Exit criteria**

- Installation is reversible and does not overwrite unmanaged gadget state.
- Production builds cannot silently use example VID/PID values.
- RNDIS is available only as an explicit documented legacy fallback.

## Hardware qualification matrix

The matrix must include at least:

- Windows 10 and Windows 11 builds currently supported by the product.
- x64 and ARM64 Windows where relevant.
- USB 2.0 and USB 3.x-capable UDCs.
- At least one non-Raspberry Pi embedded target and one Raspberry Pi target as examples, without making either a dependency.
- One-device and multiple-device host scenarios.
- Single-function NCM and any proposed composite layouts.

A CI pass cannot substitute for this matrix. Windows service binding, PnP persistence, electrical reconnect behavior, and UDC-specific descriptors remain hardware-in-the-loop concerns.

## Decision gates

- Do not implement a Windows-specific descriptor hack until standards-compliant descriptors have been captured and tested.
- Do not publish a Windows version as supported until `UsbNcm.sys` binding and bidirectional traffic are verified on that build.
- Do not add composite functions to the default gadget until their impact on enumeration and persistence is qualified.
- Do not ship example VID/PID values or per-boot generated identity values.
